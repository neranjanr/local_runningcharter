# Dual Normal / Strict Full-Tank suggestions in Estimate Fuel Economies

The Estimate Fuel Economies popup used to expose a single global `Strict Full-Tank` toggle, so the operator had to switch the whole table between lenient and strict before seeing either result. Grill 2026-09-28 asked for two suggestions per segment instead: a **Normal** column (balances in `[1, tankCapacity]`, closest to the previous economy, small steps) and a **Strict Full-Tank** column (post-Full-Tank balance driven toward `tankCapacity`), with a per-segment Apply for each and Apply All Normal / Apply All Strict. `estimateFuelEconomies` now runs the estimation pass twice and merges both suggestions onto one `SegmentEstimate` (`suggested`, `suggestedStrict`, with parallel feasibility/warning fields), so the popup can show both without a mode switch.

A Full Tank pump physically fills the tank, so a segment whose source pump is Full Tank anchors its opening balance to `tankCapacity` (previously the balance drifted across segments, making realistic economies look infeasible and the estimator fall back to absurd values such as 45 km/L). Lenient smoothing pulls interior non-Full-Tank suggestions toward the average of their neighbours and reverts any change that would break feasibility.

Considered Options: keeping the global toggle — rejected because the operator cannot compare the two outcomes or mix choices across segments. Anchoring the opening balance only in strict mode — rejected because the physical tank is full regardless of the estimation mode, and the drift bug affected lenient runs too. Strict as a penalty on the drifted source balance — rejected once anchoring made it a no-op.

Consequences: `SegmentEstimate` gains `suggestedStrict`/`feasibleStrict`/`feasibleMinStrict`/`feasibleMaxStrict`/`warningStrict`; the popup renders two suggestion columns with independent Apply buttons; with no Full Tank marks the two columns are identical. `CONTEXT.md` updates `Estimated Fuel Economy` and `Strict Full-Tank Estimation`.
